# 07 - 项目分析与优化计划

> 分析日期：2026-08-27 · 分析范围：本仓库全量源码（14,726 行 / 30 个源文件）+ MusicFree 官方移动端 + MusicFreeDesktop + 基座 zyb/musicfree-h5
> 方法：源码走读（插件加载/播放/歌词/代理/缓存全链路）+ 官方仓库结构比对 + 与自研插件（布谷音乐 v0.0.5 / 我要下歌 / 哔哩哔哩）的兼容性推演

## 0. 摘要（TL;DR）

- **项目定位**：基于社区基座 `zyb/musicfree-h5` 改造的 Web/PWA 插件化音乐播放器，订阅源已指向 `koujiao/musicfree-tianpeng`（含布谷音乐 v0.0.5）。自身不含音源，完全依赖 MusicFree 协议插件。
- **总体评价**：功能面完整（搜索/榜单/歌单/播放/歌词/离线缓存/PWA/插件订阅管理），但**协议适配层存在 4 个 P0 级缺陷**（歌词原生链死代码、duration 被丢弃、音质循环放大 API 调用、无真实沙箱），**可维护性上最大的问题是代理配置三套手工维护**。
- **与官方对比**：协议方法面 14 项全覆盖；沙箱隔离、错误语义、歌词/元数据保真度均落后官方一代；离线 PWA 与部署灵活性是 Web 端独有优势。
- **一句话方向**：先把"协议正确性"修到与官方一致（P0，约 2-3 天工作量），再做"体验与可维护性"（P1），最后向 Desktop 的功能集（本地音乐/迷你模式/备份恢复）对齐（P2）。

## 2. 架构分析

### 2.1 插件加载链（pluginHost.ts）

```
feed（远程 gitee raw → 失败回退本地 feeds.default.json）
  → downloadPluginCode(url + mirrors 逐个尝试)
  → new Function('module','exports','require','MusicFreeH5','fetch','console','env', code + '\nreturn module.exports;')
  → 识别三种导出形态：
     (a) H5 原生对象（含 searchSongs）直接用
     (b) function(hostContext) 注册式（registrations）
     (c) 官方原生对象（含 search）→ adaptMusicFreePlugin() → MusicPlugin
  → 插件代码缓存（localStorage: musicfree.plugin.code.cache）
```

**require 垫片（createRequireShim，pluginHost.ts:1380-1453）**：

| 模块 | 实现 | 风险 |
|---|---|---|
| axios | 真实库 | 无 |
| big-integer | 真实库 | 无 |
| cheerio | **DOMParser 手写垫片**（约 30 个选择器 API：find/attr/data/each/map/parent/children/filter/not…） | 高级 API 缺失时静默返回空，插件行为错误无报错 |
| crypto-js | 真实库或手写垫片 | 视打包情况 |
| qs | URLSearchParams 重写 | 不支持嵌套对象/数组 |
| dayjs | 手写垫片 | format 支持有限 |
| he | textarea innerHTML 重写 | 实体边界行为与真实 he 有差异 |
| webdav | **空实现占位**（全部方法返回空） | 官方用 webdav 做备份的插件在此端完全不可用 |
| path/url | 部分实现 | 边界用例差异 |

**env 注入**：`os:'h5'`、`appVersion:'1.0.0'`、`getUserVariables()` 经 `globalThis.__musicfree_getUserVariables` 全局注册表读取。

**代理 fetch（createProxiedFetch，pluginHost.ts:529+）**：非远程 URL 直发；媒体资源（图/音/视频）直发（注释称"无 CORS 限制"——实际取决于目标站）；其余走 `/api/proxy/<type>`（dev 用 vite 本地代理，prod 用 Netlify Function）。**响应拦截器**（pluginHost.ts:772-778）：若响应 JSON 含 `data.lrc` 且能从请求/响应提取 songmid/urlId，写入模块级 `lyricCache` —— 这是歌词的隐性来源之一。

### 2.2 播放链（App.tsx + playerStore + msePlayer）

```
setCurrentTrack → resolveStream()
  → (适配层) getMediaSource(track.extra, quality)
      quality 循环 ['standard','high','super','low','lossless','128','320']（pluginHost.ts:2047）
      任一成功返回 {url, headers?, extra:{lrc?}}；全部失败 throw '无法获取播放地址'
  → 按 stream 分流加载（App.tsx:724+）：
      ① 无自定义 headers → <audio src=url> 直接流式（唯一真流式路径）
      ② 有自定义 headers → fetch(url, {headers}) 全量下载 → Blob → audio（App.tsx:731-734）
      ③ .m4s（B 站）→ MSE：/api/biliaudio?url= 代理注入 Referer → 全量 arrayBuffer → SourceBuffer
  → 播放成功后写 songCache（IndexedDB：audioBlob + lyrics + stream 元数据）
  → 失败重试逻辑（isRetryingRef/retryCountRef，App.tsx）
```

**playerStore**：zustand persist，4 种播放模式（顺序/列表循环/随机/单曲），播放历史上限 200，partialize 保存 playlist/history/currentTrack/lyrics。

### 2.3 歌词链（App.tsx:540-650）——**核心缺陷区**

按序尝试：
1. `stream.extra.lrc`（getMediaSource 响应带 lrc）；
2. `currentTrack.extra.lrc`（注意是 `lrc` 字段，**不是**官方 `about` 字段）；
3. `nativePlugin = pluginInstance.__nativePlugin || pluginInstance`（App.tsx:588）→ 循环 6 种音质调 `getMediaSource` 找 lrc → 再调 `getLyric`（App.tsx:626）；
4. 兜底 `lyricCache`（2.1 的拦截器写入）。

**实锤问题**：`__nativePlugin` **全仓库只有 App.tsx:588 这一处读取，从未被任何地方赋值**（adaptMusicFreePlugin 返回对象 pluginHost.ts:1719-2121 不含该属性）。因此第 3 步对所有官方协议插件恒为死代码 —— **官方插件的 `getLyric` 方法在本宿主永远不会被调用**。

### 2.4 代理体系（三套手工维护）

同一份"源站 → 目标域名/头"映射表存在三份：

| 位置 | 规模 | 用途 |
|---|---|---|
| vite.config.ts | 671 行，约 100 条路由（`/proxy/xxx` + `/api/proxy/xxx` 双命名） | `npm run dev` |
| server.js | 693 行（含 /api/biliaudio 音频 Referer 代理、Range 透传） | `npm start` 本地生产 |
| netlify/functions/proxy.js | 424 行 proxyTargets 表 | Netlify 线上 |

**已观察到漂移**：Netlify 函数**没有 /api/biliaudio 对应实现**（functions 目录只有 proxy.js）→ 线上 B 站 m4s 的 MSE 路径（msePlayer.ts:41 硬编码 `/api/biliaudio`）在 Netlify 生产环境必然 404。dev/本地可用。

### 2.5 UI 与状态

- 7 个视图组件 + App.tsx 中枢（播放编排、歌词、重试、缓存协调全部在 App 组件内 —— 单体化严重）；
- pluginStore 1,918 行（安装/启用/feed/调试日志/搜索聚合未拆分）；
- 调试能力好：`subscribeDebugLogs` 请求/响应日志流 + PluginManager 可视化。

## 3. 与官方项目对比

| 维度 | MusicFree（Android 官方） | MusicFreeDesktop（官方） | musicfree-web（本项目） |
|---|---|---|---|
| 运行形态 | Kotlin 原生 App（26.4k★） | Electron（electron-forge）多窗口：renderer / renderer-lrc / renderer-minimode + Web Workers（8.8k★） | 浏览器 PWA（React 18 + Vite 5） |
| 插件沙箱 | **独立进程**隔离 + 10s 超时 | renderer 层加载（协议与移动端完全一致） | **new Function 同页执行**，无隔离（见 P0-4） |
| 协议方法（14 项） | 全量 | 全量 | 方法面全覆盖，**getLyric 接线断裂**、getMusicInfo 未实现 |
| require 白名单 | axios/cheerio/crypto-js/dayjs/big-integer/qs/he/webdav 真模块 | 同移动端 | axios/big-integer 真实；**cheerio/qs/dayjs/he 手写垫片**；webdav 空实现 |
| 媒体自定义 headers | 宿主网络层支持（真流式） | 支持 | 仅 fetch+blob 全量缓冲 / MSE 全量缓冲（无真流式代理） |
| 歌词 | 完整 getLyric 协议 + LRC 渲染 | + 独立 LRC 窗口（renderer-lrc、link-lyric 同步） | 有解析渲染，但获取链断裂（2.3） |
| 本地音乐 | ❌ | ✅（local-music + File System） | ❌ |
| 迷你模式 / 备份恢复 | — | ✅（renderer-minimode / backup-resume / WebDAV） | ❌（webdav 空实现） |
| 离线能力 | 有限 | 有限 | ✅ **PWA + IndexedDB 全曲缓存 + SW 缓存（本项目最强优势）** |
| 部署 | APK | EXE | Netlify 静态+Serverless（海外中转 + 免费层限制）/ 本地 Node 服务 |
| 插件更新 | 订阅源 + 版本管理 | 同 | 订阅源 + 本地 fallback feed（已具备雏形） |

**结论**：Web 端把"插件化 + 浏览器部署 + 离线 PWA"跑通了，是官方生态缺位的形态；但协议实现质量（错误语义、歌词、元数据保真）与安全隔离落后官方一代，当前差距主要来自"手写垫片 + 死代码"而非架构不可行。

### P1 —— 体验与可维护性

5. **分页断裂**：getTopListDetail 硬编码 page=1（pluginHost.ts:1922）、getMusicSheetInfo 固定第 1 页（pluginHost.ts:1852）→ 榜单截断在前 20-22 首（酷狗 TOP500 共 500 首、酷我 300 首）。

11. **单体化**：App.tsx 1,483 行（播放/歌词/重试/缓存协调全在组件内）、pluginStore 1,918 行。

### P2 —— 打磨

12. 大量 console.log（含大 JSON.stringify，泄露带签名参数的 URL）；proxyMediaUrl 空函数（死代码）；isMSERequiredAudio 仅识别 .m4s；单 bundle 645K 未分包。

## 5. 与自研插件的兼容性（布谷音乐 v0.0.5 / 我要下歌 / 哔哩哔哩）

| 能力 | 预期 | 依据 |
|---|---|---|
| 搜索/榜单/歌单 | 基本可用 | 适配层方法齐全；布谷用 cheerio 基础选择器（find/attr/text/each/slice），垫片已覆盖 —— 需一次实测确认 |

**推论**：在 P0 修复前，布谷音乐 v0.0.5 在这台 Web 宿主上的体验 ≈ 只有"能搜能播（慢）"，歌词与错误提示两大卖点全部丢失。

## 6. 后续优化计划（按 P0 → P1 → P2）

### P0 协议正确性 —— 修到与官方一致

**已完成（M1，2026-08-27，e2e 实机验证）**：① getLyric 接线（__nativePlugin Proxy 注入，七里香(Live) 实测 18 行歌词）② duration 透传 ③ 单音质 + 错误透传（getMediaSource 单首恰 1 次，原最坏 13 次）④ 代理白名单补齐（P0-5）⑤ 最小沙箱（localStorage shim + fetch/XHR 审计）。

**剩余 4 项（3-5 天）**：

- **P0-1 分页贯通**（榜单/歌单详情当前截断在前 20-22 首）
  改点：pluginHost.ts getTopListDetail 适配器（约 1922 行）与 getMusicSheetInfo（约 1852 行）page 硬编码 1 → 透传调用参数，按插件返回 isEnd 终止；pluginStore.ts toplist/sheet 缓存加 {page, hasMore}；PlaylistView.tsx/SearchView.tsx 滚动到底自动加载
  *验收：酷狗 TOP500（22 首/页×25 页）翻满 500 首；酷我 num 分页终止正确；QQ 榜 isEnd 不重复加载*

- **P0-2 getMusicInfo 实现**（协议 14 方法唯一未适配项）
  改点：types/plugin.ts 加接口；pluginHost.ts 适配层 raw 原生有该方法时透传（runInPluginContext 包裹）并归一化 duration/picurl/about
  *验收：e2e 调用返回源方元数据*

- **P0-3 协议 14 方法一致性核对**（一次性审计）
  做法：对照官方插件协议文档逐方法核对适配层（search / getMediaSource / getLyric / getMusicInfo / getTopLists / getTopListDetail / getRecommendSheetTags / getRecommendSheetsByTag / getMusicSheetInfo / importMusicSheet / importMusicItem / getSearchSuggestions…），输出 ✅/⚠️/❌ 核对表归档 docs/07；重点查语义偏差（search type 参数、topListItem/sheetItem 回传、isEnd 判定、字段命名）

- **P0-4 错误语义对齐**（P0-3 遗留）
  做法：getMediaSource 失败分类透传（未收录/付费/限流/网络），Error 带 code，UI 按 code 显示；RATE_LIMIT_EXCEEDED →「音源繁忙，请稍后重试」
  *验收：付费歌显示"该歌曲为付费内容…"，限流歌显示限流提示而非笼统的"无法获取播放地址"*

### P1 体验与可维护性（1 月，M2 出口后启动）

1. **代理单一事实源**（最高优先级，含 M1 遗留）：新增 `src/lib/proxyTargets.ts` 单表 `{key, target, allowHtml, headers}`，vite/server.js/netlify 三处同表生成；按 target 加 allowHtml（y.qq.com / www.kugou.com / www.kuwo.cn 的 SSR 页面）解决 `netlify/functions/proxy.js:370-388` 拒收 `<!doctype` 的问题（线上布谷榜当前因此不可用）。*验收：三套代理一致性单测 + Netlify 线上榜单页 200。*
